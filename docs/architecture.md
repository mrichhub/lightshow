# Architecture and decisions

## Ownership

The API uses a database-scoped read/write MongoDB account; the engine uses a separate read-only account. Root credentials are confined to bootstrap containers. Compose passes each application only the environment secrets it needs. The broker mounts its leaf key and certificate, without mounting its private CA signing key.

MongoDB 8 is the persistent authority for devices, their configuration, logical elements, scene effect parameters, desired show selection, revocable sessions and token hashes. Runtime diagnostics live separately in `device_status`, replacing the current record rather than appending every five seconds. Device IDs are six cryptographically sampled uppercase alphanumeric characters, with collision retries and unique database indexes for both ID and hardware identity.

The API owns configuration writes and administrator/device authentication. A replica-set transaction increments a common mapping revision document before validating and writing any device or element mapping. This serializes competing mapping mutations, so two editors cannot independently introduce an overlap. Device edits additionally use `expectedVersion` to reject lost updates. A board profile cannot change after enrollment.

The engine owns active scene time, rendering, manual overrides, mappings and DDP output. The API writes desired scene selection and override definitions in the singleton `shows/desired` document; it never composes pixels. The engine acknowledges its current scene and configuration version through retained MQTT show state. Persistent `startedAt` makes elapsed scene time stable across reloads and restarts. There is no advanced playlist scheduler in this initial release.

An ESP knows only physical outputs and modes. In listening mode it receives a flattened RGB frame: concatenate outputs in configuration array order. `outputIndex` always refers to that array position, independently of a stable output `id`. The device translates canonical RGB into configured wire color order. Local mode uses a built-in dim rainbow and remains reachable through REST/MQTT. Element debugging stays in the central renderer and does not change a whole device's mode.

## Rendering and mappings

Every logical pixel must map exactly once. Physical segment ranges reserve all their pixels, including skips, and cannot overlap another segment. Skips are zero-based relative to their segment, not absolute output indexes. They consume physical range but no logical index. Bounds, duplicate skips, output existence and complete logical coverage are validated when configuration changes. Elements can span outputs and devices.

The engine precompiles lookup tables, effect closures and logical/physical buffers. Each frame clears buffers to black, renders scene effects (later effects replace earlier effects on a shared target), applies logical overrides, maps logical pixels, applies output overrides, then forces skipped pixels black. Pixels outside mapped segments are black except when explicitly testing a whole physical output. Individual-pixel overrides leave the other scene pixels intact. There are no database reads in the frame path.

DDP uses the version-1 10-byte header, RGB24 datatype `0x0b`, display ID 1, big-endian byte offsets/lengths, per-packet sequence 1–15 and Push only on the final packet. Payloads default to 1440 bytes, below Ethernet MTU. UDP packet buffers are reused only after all send callbacks finish; a busy destination drops the next frame instead of queuing latency. Receiver assembly accepts contiguous ordered packets beginning at offset zero. A sequence gap, offset mismatch, truncated frame or missing Push discards the incomplete frame; the next offset-zero packet recovers. Reordered packets are deliberately dropped. The initial implementation supports full frames, not sparse partial DDP updates or timestamp extensions. No command or authentication data is added to DDP.

Receivers reject unlisted sources before handling pixel payloads. The first valid sender holds an exclusive source lock until no valid packet arrives for the configured timeout. Valid permitted packets extend the listening timer even when the frame remains incomplete; incomplete frames never become visible. Local mode is exempt. IPv4 source filtering is not cryptographic authentication; deploy DDP within the trusted lighting network.

## Events and failure recovery

One MongoDB Change Stream per API instance fans status/configuration/show events out to SSE clients. Each client gets a complete initial snapshot. The broadcaster sends keepalives, removes disconnected clients, drops slow consumers and periodically emits freshness transitions even without heartbeats. Browsers also compute freshness from server timestamps. On stream errors the API reconnects and sends a reconciliation snapshot. Events are ephemeral; browser reconnection always starts with a new snapshot rather than relying on replay IDs.

Configuration persistence completes before a QoS 1 notification. The API's Change Stream also publishes notifications for committed device/configuration changes. A device compares versions and fetches the REST configuration. Reconnect fetches and heartbeat version comparisons recover missed MQTT notifications. Commands are never retained. The engine listens for MQTT notifications and reconciles MongoDB every five seconds, including new device addresses; database failures leave the last fully validated renderer in place and make its health endpoint fail when reconciliation remains stale.

Heartbeats carry connectivity and operational diagnostics separately. Online is at most ten seconds old, warning is ten to twenty seconds, and offline is over twenty seconds. A current heartbeat can still have degraded operational health due to a last error, disconnected interface or low heap. No unbounded heartbeat history is retained.

## Authentication boundaries

Administrators use an Argon2id password and opaque server-side sessions with expiry and immediate revocation. Cookies use the `__Host-` prefix, Secure, HttpOnly, SameSite=Strict and Path=/. Cookie mutations, including login, require an exact configured Origin. Script/Swagger tokens are independent random 256-bit opaque values, hashed in the credentials collection and separately revocable. Login rate limits use the direct connection peer; behind Caddy this deliberately limits the whole local deployment rather than trusting forwarded addresses from arbitrary callers.

Device enrollment requires an expiring, one-use token bound to an exact hardware identity, issued by an authenticated administrator. Identity and credential creation plus token consumption occur transactionally. A public MAC never grants enrollment or replacement. Subsequent init calls require the existing REST token. If first enrollment loses its response, the administrator revokes/deletes the orphan record and reissues enrollment; retrying the consumed token reveals no secret. Tokens cannot be recovered from the database because only their SHA-256 hashes are stored. The random token entropy makes an adaptive password hash unnecessary for these opaque tokens.

MQTT is a separate trust boundary: the API provisions a separate random password through Mosquitto's Dynamic Security control protocol, scoped to one device's command/state/availability/telemetry topics. A successful authenticated init rotates that MQTT password and returns it over validated HTTPS. Devices retain the REST credential and can recover an interrupted MQTT setup by repeating authenticated init. Mosquitto persists salted PBKDF2 hashes, never plaintext MQTT passwords. The API has the broker control role; the engine has show and configuration-notification permissions only. Revocation disables the MQTT client before removing the REST token, and remains retryable if broker administration fails.

HTTPS and MQTT use certificate validation with deployment public CA trust, including hostname verification. Credentials are not placed in URLs or logs. Firmware NVS and the simulator's mode-0600 identity file necessarily contain their device secrets. Protect physical flash access; flash encryption and secure boot are deployment hardening options not automatically enabled here.

## Offline and hardware assumptions

The six main services use ARM64/x86-64 images, persistent storage and health checks. MongoDB 8's ARMv8.2-A requirement means Pi 5 or another compatible database host is required. Local DNS, LAN reachability and accurate time are infrastructure prerequisites. Caddy creates its private CA once and retains it in a volume; separate broker CA material is generated privately at setup. All frontend assets are bundled with system fonts. Internet access is needed only for provisioning/downloads.

Firmware uses Arduino-ESP32 2.0.17 / ESP-IDF 4.4 via PlatformIO 6.12.0 and FastLED 3.9.15 RMT4. It pins lighting to core 1 and primary network work to core 0, with a separate core-0 HTTPS worker. Three pointer-swapped RGB buffers avoid ownership races when UDP receives while FastLED transmits; pending frames are replaced by the newest complete frame. A separate CRGB output array permits color-order conversion without modifying received pixels. These buffers use roughly 48 KB at the 4096-pixel cap. FastLED RMT4 multiplexes registered pins; physical output duration can exceed the requested 25 ms for long strings, so 40 FPS is a target, not a promise at every output size. Measure on actual hardware.
